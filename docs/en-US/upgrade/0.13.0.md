# 0.13.0: drawing alerts and responsiveness

This page describes the local 0.13 candidate. npm publication is separate; published 0.12 packages do not contain these new APIs.

Select a drawing and choose Add alert, or open Drawing alerts. Supported sources are confirmed chart-local horizontalStraightLine, straightLine, segment and rayLine drawings on the default main price axis, with market anchors and existing market interpolation. Local and confirmed backend sources retain their original authority and backendId. Alert operations do not write annotations or orders.

Use executeDrawingAlertCommand with create/update/pause/resume/rearm/delete. Conditions are crossing/crossing-up/crossing-down, frequencies once/once-per-bar. Pause/resume retain triggered and last-bar markers. Rearm clears markers, preserves instance history and seeds the first observation. A triggered once rule requires rearm. Updating condition/frequency clears comparison points, retaining markers; changing only message retains the comparison point.

Only observed closes are evaluated, including same-bar replacements. No path is inferred from OHLC high/low. There is no tick-touch, bar-close, historical catch-up or background monitoring guarantee. Segments remain finite and rays retain direction. Slopes use actual bar positions across market closures. Log axes interpolate log prices; normal/percentage axes use the affine price domain. Reversal affects display only.

`trading-chest/alerts` exports evaluateDrawingAlert, validation and portable types as DOM-free ESM/CJS. It has no runtime dependency on KLineCharts, Solid, React, CSS or storage. The caller supplies confirmed geometry, real bar timestamps, previous/current observations, markers and axis type. The function returns new markers, an optional comparison point and at most one event; it sends no notifications.

Chart options add onDrawingAlertStateChange/onDrawingAlertTrigger/onReplayDrawingAlertTrigger. Live and replay keep separate points, markers and up to100 instance records. barTimestamp is the observed market bar timestamp, not a fabricated tick time.

captureDrawingAlerts/restoreDrawingAlerts use a separate DrawingAlertDocumentV1. A stable opaque drawingAlertScope is required across reopening. Restore validates the complete document before replacing rules, keeps the old rules on failure, and always restores paused with deduplication markers. Layout v4/workspace v2/shared v1/preferences v1 do not gain alert fields. Layout-only saves do not save alerts. The drawing-workbench alerts.html page demonstrates native IndexedDB atomic bundle storage and a new independently fed staging chart, adopted only after layout and alert restoration both succeed.

Datafeed/HTTP/ChartSnapshot signatures stay unchanged. applySnapshot now matches actual optional ticker/market/exchange/priceCurrency fields and period. Capture the request identity before an asynchronous read; do not relabel an old response with the current identity. A same-series full HTTP snapshot may evaluate only a last-bar replacement or one append; multiple missing bars, earlier revisions or basis changes seed only the latest observation. Internal per-bar writes do not backfill alerts. Disconnects, errors, revisionRequired, unconfirmed data and real restoration clear comparisons; status-only events cannot reevaluate a quote.

curve/doubleCurve/arc add startMarker/endMarker (none/arrow/circle, default none), background (default false) and finite backgroundOpacity in[0,1] (default0.12). The standard overlay.styles.polygon.color supplies the fill, defaulting to the actual stroke. The background closes the curve with its endpoint chord; it does not extend to a price baseline or pane edges. Markers use outward endpoint tangents and6–18 CSS px sizes from the resolved width. Fills ignore hits; markers do not add control points. Old definitions keep their appearance, the catalog remains56 tools, and the original0.5px/2048-segment bounds remain. Full parameter templates remain same-tool; explicit cross-tool common-style templates transfer only declared style capabilities.

Batch optimization retains per-object confirmations, guards, observable state, ordered results and one undo transaction. Actual performance acceptance belongs to complete raw samples and the implementation SUMMARY, separately from package and functional validation.
